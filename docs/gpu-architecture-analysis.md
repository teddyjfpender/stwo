# CUDA backend architecture analysis: where the 10-20x lives

*Produced by a three-lane code-level analysis (sync/launch census, NitrooZK
orchestration comparison, host-roundtrip inventory) plus an adversarial
cross-check that verified every load-bearing claim against the source. This is
the blueprint for the re-architecture; no further GPU benchmarking until the
blocking measurements below are taken.*

## Verdict

The backend is **latency-bound by construction, not compute-bound**. The kernels
are fine; the orchestration serializes the GPU against the host at every step:

1. **Every wrapper ends in `cudaDeviceSynchronize`** - 83 static sites; no two
   GPU operations can ever overlap, including calls issued concurrently from
   rayon threads (they serialize on the device-wide sync).
2. **The allocator is a hidden multiplier**: every device alloc/zero/free
   creates a private CUDA stream, syncs it, and destroys it
   (`cuda_mem_pool.cuh:90-169`). ~4,000-6,000 alloc events per prove =
   8,000-12,000 extra blocking API calls.
3. **Zero pinned memory anywhere** - every H2D/D2H copy is synchronous pageable.
4. **Per-column loops where batched kernels exist**: commit *evaluation* runs one
   NTT per column (~1,700 launches / ~2,100 device syncs per Cairo prove) while
   commit *interpolation* right next to it is properly batched by log size; the
   batched OODS entry point exists but is `#[allow(dead_code)]`.
5. Assorted waste verified at the source: FRI fold clones uninitialized buffers
   3x per call; the JIT lane's accumulate pass is a separate kernel though the
   fused path is already plumbed; `from_simd_evals` dropped the default impl's
   rayon parallelism; the NVRTC kernel cache is in-process only (every new
   process recompiles every component).

NitrooZK's same-lineage kernels hit 10-20x because their host code maintains the
opposite discipline: stream-ordered allocation, deferred synchronization (sync
only at Fiat-Shamir/host-read boundaries), batched per-phase kernels, pinned
transfers, and persistent warm state.

## Blocking measurements (before any rebuild work)

- **nsys timeline of one fib-1M prove**: GPU-busy %, idle-bubble share, NVRTC
  wall share. The identified steady-state savings sum to ~2-4s against a
  13.2s -> <2s target, so either idle bubbles dominate beyond the raw
  API-latency floor (likely, given ~10k blocking events) or kernel-throughput
  work is also needed.
- **One timing print around `compile_kernel`** to settle the NVRTC share.
- Count actual columns (~200 vs ~420 disagreement between lanes) and OODS
  weight entries (1-3 vs 15-30) from a real run; both scale transfer estimates.

## Ranked re-architecture plan

### 1. Stream-ordered execution rewrite (the NitrooZK sync discipline)
- **What changes:** Remove `cudaDeviceSynchronize` from all 83 wrapper sites; allocator becomes stream-ordered (`cudaMallocFromPoolAsync`/`cudaFreeAsync` on stream 0, no private stream create/sync/destroy); all copies become `cudaMemcpyAsync`; host syncs only at genuine read boundaries (Merkle roots for Fiat-Shamir, claimed sums, OODS readback, decommit gathers). Single stream — no multi-stream complexity needed (NitrooZK proves this works).
- **Expected saving:** 0.5-1.5s direct API/stall removal, but the real upside is structural: launch-bound phases (per-column NTT, Merkle layers, OODS reductions, FRI folds) become continuous launch chains. If GPU-busy is low (likely, given ~10k blocking events), saving is multiplicatively larger. Prerequisite for items 3-5 to pay out fully.
- **Byte-equality risk: MEDIUM** — not from math (same-stream ordering preserves values exactly) but from unfenced host reads/use-after-free once syncs vanish. This exact bug class corrupted Metal proves twice (queue_drain fence; unfenced `to_vec`). Every host-read primitive (`to_vec`, `Column::at`, `get_data`) needs an explicit stream sync. Gate with the existing repeated-prove byte-equality conformance tests on RTX 3090.
- **Size: L** (83 wrapper sites + allocator + utils.cuh copy primitives + Rust-side fencing).

### 2. JIT lane caching: persistent NVRTC cache + Rust-side recording/codegen cache
- **What changes:** Disk-persist compiled PTX/cubin keyed by (semantic hash, GPU arch) in `runtime_jit.cu`; add a Rust-side `(component TypeId, log_size)`-keyed cache of `lower_framework_eval_to_v1_with_logup` + CUDA source emission (claimed_sum is already parameterized out, so the artifact is prove-invariant).
- **Expected saving:** 5-20s on first prove per process — if the 13.2s benchmark is a cold process, plausibly the single largest chunk; plus 0.1-1s/prove of host-serial recording/codegen at Cairo scale even warm.
- **Byte-equality risk: NONE** (identical kernels, identical math). One caution: key by content hash + arch, never by pointer — pointer-keyed twiddle-cache aliasing was a real prove-corrupting Metal bug.
- **Size: S** (disk cache) **+ M** (Rust-side cache).

### 3. Batch evaluation + OODS (mirror the two batched paths that already exist)
- **What changes:** (a) Override `evaluate_polynomials` on CudaBackend to mirror `interpolate_columns` — group by log_size, one `ntt_n2b_columns` with `num_poly=group`, drop the extend+copy_from double buffer (collapses ~1,700 launches/~2,100 syncs to ~tens). (b) Wire the dead `cuda_batch_eval_at_point` into the pcs driver grouped by (log_size, point) — kills ~520 per-pair 16-byte sync readbacks and ~2,600 events. (c) Move barycentric weights fully on-device (point-vanishing kernel + existing batch_inverse) — kills the 4-64MB pageable uploads and the single-threaded host `batch_inverse_in_place`.
- **Expected saving:** 0.3-1.0s steady-state; more once #1 lands.
- **Byte-equality risk: LOW** — M31/QM31 arithmetic is exact modular arithmetic, so reduction/batching order cannot change values (unlike floating point). Only requirement: OODS results must be mixed into the channel in the identical (tree, column, point) order. Batch inversion (Montgomery's trick) yields bit-identical inverses.
- **Size: M.**

### 4. Witness ingestion: pinned, batched, overlapped upload
- **What changes:** Pack SIMD columns into large pinned staging buffers; few async H2D copies overlapped with `to_cpu()` unpacking (pipelined chunks); allocate device buffers uninitialized (drop the redundant per-column memset in `copy_uint32_t_vec_from_host_to_device`); restore the rayon-parallel unpacking dropped by the `from_simd_evals` override (backend.rs:73-106).
- **Expected saving:** 0.3-1.0s (1.6-3GB pageable serialized H2D today; pinned ~2x PCIe efficiency, overlap hides most of the rest).
- **Byte-equality risk: NONE** (same bytes). Pinned+async reintroduces the host-read race class — staging buffers must outlive the copy; same-stream ordering covers device consumers.
- **Size: M.** (The full NitrooZK answer — witness born on device — is XL and blocked by stwo-cairo's 86K LoC generated SIMD witness; out of scope.)

### 5. Copy/alloc waste bundle (the residue once 1-4 land)
- **What changes:** (a) Replace `CudaSecureColumn::new_with_size`'s 3 garbage D2D clones with 4 independent uninitialized allocs (secure_column.rs:13-24). (b) Fuse accumulation into the JIT kernel — `accum_coords` is plumbed and deliberately discarded (jit/mod.rs:111) — and drop the 4 redundant scratch zero-fills. (c) Device-side `extract_subdomain_twiddles` + borrow instead of full-buffer clone (quotient.rs:161-174). (d) `join_at_mid`/`split_at_mid` as D2D kernels (64MB/prove composition split; mandatory before low-memory mode is usable on CUDA at all — currently 3-8GB PCIe). (e) Batch the quotient tail's 4 coordinate NTTs into one interpolate_columns-style call. (f) Device-side `pack_leaves_input` (runs for BOTH channels).
- **Expected saving:** 0.1-0.4s aggregate at fib-1M.
- **Byte-equality risk: NONE** — all produce identical values; (b) is exact field addition with the transcript untouched.
- **Size: S each, M total.**

**Honest total:** items 1-5 sum to ~2-4s steady-state plus 5-20s cold-start. If nsys shows the 13.2s is mostly NVRTC + idle bubbles, <2s is reachable with this list. If GPU-busy is already high, <2s additionally requires kernel-throughput work (FFT stage fusion, fused Merkle leaves a la NitrooZK blake2s.cu:399-452) that this list does not cover.

## Claims flagged as wrong or needing verification before acting

1. **WRONG IMPLICATION — "enable the precompiled constraint lane" is not a viable shortcut.** Verified in `/Users/theodorepender/code/personal/stwo/crates/backend-cuda/src/backend/constraint_eval.rs:81-91`: the staged kernels were generated against NitrooZK's stwo v2.1.1 + *their* AIR revision and showed 100%-of-rows mismatches on every component; the lane is opt-in via allowlist with a verify-mode qualification path. The 258 stream-syncs in those files are irrelevant until kernels are regenerated against this AIR. JIT caching (#2) is the correct path.
2. **Unverified premise: "<2s achievable by re-architecture alone."** The analysis quantifies no GPU-busy time and its own savings sum to ~2-4s steady-state. Needs nsys before roadmap commitment.
3. **NVRTC share of the 13.2s** — unmeasured, arithmetic tension with the 5-20s claim (see consistency point 2). Highest-priority single measurement.
4. **Column count (420 vs 200) and OODS weights count (15-30 vs 1-3)** — the two sections disagree by 2x and 10x respectively on the same workload; both scale top-line estimates. Count them from the actual fib-1M run.
5. **Correct and load-bearing: the NitrooZK pageable-async-D2H note.** `cudaMemcpyAsync` D2H to *pageable* memory blocks the host; naively switching such sites to pinned memory creates a race. Every sync removed in item 1 and every pinned conversion in item 4 must add an explicit sync at host-read boundaries — Metal corrupted proves twice via exactly this class.
6. **Minor: census "fold_step=1 skips PackLeavesOps" vs inventory "pack_leaves_input runs per packed FRI layer"** — both true (it runs only when packing applies); whether item 5(f) matters depends on the Cairo FRI config's fold_step. Check before building it.
7. **Allocator free-path overhead slightly overstated** — `cuda_allocator_free_for_proving` only syncs when `use_mem_pool` is true (cuda_mem_pool.cuh:148-169); doesn't change the conclusion.

## Lane reports (full findings)

### Lane: sync-launch-census

Synchronization census of the CUDA backend: every exported kernel wrapper in backend-cuda-kernels launches on the legacy default stream and ends in cudaDeviceSynchronize (83 static device-sync sites; 259 stream-sync sites of which 258 are in the disabled precompiled constraint kernels and 1 is the allocator's primitive; 30 synchronous pageable cudaMemcpy sites; zero pinned memory). The dominant hidden multiplier is the allocator (cuda_mem_pool.cuh:90-169): every device alloc/free creates, syncs, and destroys a private CUDA stream. Hot-path tracing of a fib-like Cairo prove (~46 components, ~420 columns, log 18-21) shows: witness upload = 1 pageable sync memcpy + 1 zero-fill ctx per column (~420 each); interpolation is batched per log-size (~15 NTT calls, 5 syncs each) but extension/evaluation is per-column (~424 NTT calls, ~1,700 launches / ~2,100 syncs — worst phase); Merkle commits launch+sync once per tree layer (~92 events main trees, ~220 more for the 17 per-layer FRI trees); JIT constraint eval is 2 launches + ~14 blocking events per component plus a 5-20s one-time NVRTC cost; OODS does an unbatched 3-4 launch+sync chain plus a 16-byte sync readback per (column,point) pair (~520 pairs, ~2,600 events) plus 4-64MB pageable weight uploads; the quotient tail adds a 24MB twiddle host roundtrip and 4 unbatched interpolate+evaluate chains; each FRI fold wastes 3 full-size D2D copies in new_with_size. Totals: ~4,500 kernel launches, ~8,500-12,000 blocking sync events, ~2,300 synchronous memcpys, ~5,000 stream create/destroy pairs, giving a re-architecture-addressable latency floor of roughly 0.5-1.0 s per prove (0.16-0.48 s pure API round trips + 0.3-0.7 s pageable transfers), plus 5-20 s NVRTC on the first prove.
